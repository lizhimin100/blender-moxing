# 硬边 RTS 资产包

一套俯视角 RTS 用的低模资产：**建筑 17 座 / 单位 7 件 / 地形 4 套**，全部 glTF 2.0 二进制（`.glb`），
**贴图内嵌，不依赖任何外部图片或 `.bin`**。1 unit = 1 m，原点在占地中心，地面 z = 0。

```bash
git clone https://github.com/lizhimin100/blender-moxing.git
```

---

## 0. 我要导哪个文件

**游戏里只用 `_手游_近 / _手游_中 / _手游_远` 三档**，其余是出图和源数据。

| 你想干的事 | 用哪个文件 |
|---|---|
| 进游戏（近景，0–45 m） | `<资产>_手游_近.glb` |
| 进游戏（中景，45–90 m） | `<资产>_手游_中.glb` |
| 进游戏（远景，90 m+） | `<资产>_手游_远.glb` |
| 建造动画 | `<资产>_建造.glb` |
| 出图 / 图标 / 特写 / 做新 LOD | `<资产>.glb`（细分档，**不要进游戏**） |
| 做碰撞体 / 调试拓扑 | `<资产>_低模.glb` |
| 建造按钮卡面 | `<资产>_图标.png`（512²，已裁好） |

单位不一样：多数只有**单档本体**（见 §4），直接导本体。

## 2. 那些数字是什么意思

### 2.1 tri = 三角面数

GPU 只会画三角形，一个四边面 = 2 个三角。`6,768 tri` ≈ 3,400 个四边面。
RTS 建筑的经验区间是 **5k–20k**；渲染一屏几十座时，瓶颈通常不是 tri 数而是**材质数**。

### 2.2 六个档位

以「地牢入口」为例，同一个模型出六份：

| 文件 | tri | 材质 | 是什么 |
|---|---:|---:|---|
| `地牢.glb` | 15,488 | 19 | 倒角 + 一级细分烘焙后的版本。**出图与图标用它**，游戏别导 |
| `地牢_低模.glb` | 6,768 | 19 | 细分前的拓扑，全平面着色。是新 LOD 的源 |
| `地牢_手游_近.glb` | 6,768 | **4** | 低模 + 打图集。**游戏 LOD0** |
| `地牢_手游_中.glb` | 1,988 | 3 | 按包围盒体积砍掉小件 |
| `地牢_手游_远.glb` | 1,180 | 2 | 再砍一档，1–2 px 的东西不留 |
| `地牢_建造.glb` | 9,580 | 10 | 本体 + 脚手架，带 `build` 动画（39 通道） |

两个关键点：

- **细分档是 2–4 倍面数**。地牢 6,768 → 15,488；折壳入口 7,112 → 36,526。
  只盯细分档的数字会误判性能，**看手游档**。
- **材质数从 19 降到 4 是打图集换来的**。桌面档每个纯色材质单独一个槽（最多 19 次 draw call），
  手游档把颜色烘进一张 UV 图集的格子，合并成 `主体`（图集贴图）+ `自发光`（火焰）+ `team` + `team_trim`。
  这就是「4 材质」的全部含义。

### 2.3 为什么近景 LOD 和低模 tri 数一样

因为打图集只改 UV 和材质，**不动几何**。中/远景才真正减面。

## 6. 阵营色

**只改 `team` 和 `team_trim` 两个材质的 `baseColorFactor`，不要碰 `主体` 和 UV。**

| 阵营 | team | team_trim | 现状 |
|---|---|---|---|
| 联盟 | `#2E5FB4` 蓝 | `#F1CD79` 金 | 默认值，引擎按玩家改 |
| 失落帝国 / 失落 | `#743A2E` 氧化铁红 | `#A99578` 灰骨粉笔 | 中立，**不建议再换色** |

失落为什么不是蓝：那几座是中立废墟，套联盟蓝会一眼读成「人族据点」。
它们的 `team` 材质名仍然叫 `team`（引擎按名字找），只是基色被覆写成锈红。

`team_trim` 的面积只有 `team` 的 1–5%，是一条 3–6 cm 的边线，不是填充色 ——
刷大面积会立刻变成「蓝金二色砖」，这是这套资产最容易踩的坑。

## 7. 进 Godot

1. 把 `.glb` 拖进 `res://`，**导入预设默认即可**：贴图内嵌在 GLB 的 BIN 块里，没有外部依赖。
2. **朝向**：建模期正面是 +Y，导出后是 **−Z**，和 Godot 的 `Node3D.forward` 一致，`yaw = 0` 即正面朝前。
   原点在占地中心、地面 z = 0，直接摆到地形高度上，不用补偏移。
3. **三档 LOD** 用 `GeometryInstance3D.visibility_range`：
   近 `0–45`、中 `45–90`、远 `90–160`（按 RTS 相机高度估的起点，实测再调）。
   远景档里 1–2 px 的构件已经删掉，硬切看不出来，不需要 fade。
4. **建造档**：`animation_player.play("build")` 驱动脚手架进出；
   建筑本体从下往上显影靠材质里的世界高度裁剪（uniform `reveal_height`），
   **本仓库不含那个 shader**，见 §9。
5. 火焰类资产走 `自发光` 材质，不需要额外点光；洞内不要再补灯，会毁掉明度秩序。

## 10. 本仓库不收什么，为什么

| 不收 | 理由 |
|---|---|
| 渲染迭代图（约 50 MB） | 是过程不是资产。图标已经代表每一座 |
| `_历史版本/` | git 本身就是版本管理，再存一份是重复建设 |
| `.blend` / `.pyc` / `_tmp` | 中间产物，重跑脚本就有 |
| **生成脚本** | 本仓库只做交付。**要改模型得回源工程**（Blender 4.x + 建模脚本链），不在仓库里 |

最后一条是有代价的：拿到这个仓库的 agent 能**用**、能**读懂为什么**，但**改不了**。
如果哪天要把仓库做成可再生的，把源工程的 `blender/bs_v6/*.py`（约 1.8 MB，纯文本）
一起放进来即可 —— 几何本来就是代码。
